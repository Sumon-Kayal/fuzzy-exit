# Tests

Two scripts, no external test framework or dependencies beyond Bash and awk.

    tests/run_tests.sh               unit tests for __fuzzy_exit_match
    tests/install_uninstall_test.sh  end-to-end test of install.sh / uninstall.sh

Run both from the repo root:

    bash tests/run_tests.sh
    bash tests/install_uninstall_test.sh

## Why the fixtures look like this

`__fuzzy_exit_match` only ever accepts strings that start with `"ex"` — that
anchor check runs before anything else. So for any fixed input length, the
*entire* decision boundary is just "every string of that length starting with
`ex`". For 4-character input that's exactly 676 strings (`ex` + any 2 of 26
letters), out of the 456,976 total in `fixtures/all_4_character_combinations.txt`.

`run_tests.sh` uses that to stay both fast and exhaustive where it matters:

- All 676 `ex`-prefixed candidates are tested for real, every run, and diffed
  against `fixtures/expected_matches.txt` (52 words). Nothing here is sampled.
- The remaining ~456k non-`ex` strings are the safety property ("unrelated
  typos stay untouched") — a deterministic stride sample of ~3,330 of them is
  tested for real on every run. Run with `--full` to test literally all of
  them for real instead of sampling (~15 minutes; this is what the weekly
  `full-corpus` CI job does — see `.github/workflows/ci.yml`).

`fixtures/expected_matches.txt` isn't hand-written. It's generated by
`generate_expected_matches.py`, a from-scratch reimplementation of the
matching rules in Python — a different language than fuzzy-exit.sh, so a
transcription slip in one is unlikely to also appear in the other. Only
re-run it if the matching rules in fuzzy-exit.sh intentionally change:

    python3 tests/generate_expected_matches.py > tests/fixtures/expected_matches.txt

`fixtures/exit_all_permutations.txt` (the 24 anagrams of e/x/i/t) is a
smaller, human-readable sanity check on the same anchor rule: only `exit` and
`exti` start with `ex`, so those are the only two of the 24 that should match.

## A behavior worth knowing about

The matcher is structural, not a dictionary of "exit"-like typos — it accepts
any 4-character `ex??` string with an `i` in the third slot or a `t` in the
fourth (plus a couple of explicit cases), and any 5-character `ex???` string
that becomes "exit" after dropping one character. That second rule means
ordinary English words can match if they happen to fit: **`exist`** does
(`exi` + `s` + `t` — drop the `s`), same as the documented `exxit` example.
This isn't a bug in the tests or the matcher — `run_tests.sh` asserts `exist`
*does* match, because that's what the shipped algorithm actually does — it's
just a real edge case: if a 5+-character word like this isn't installed as a
real command, typing it will close the shell instead of giving
"command not found". Worth keeping in mind if the matching rules change.
